# 校园论坛 · 数据库设计文档

> 数据库 `template`　MySQL 8.0　字符集 `utf8mb4` / `utf8mb4_0900_ai_ci`　存储引擎 InnoDB
>
> 建表脚本：[`Jwt-backend/sql/schema.sql`](Jwt-backend/sql/schema.sql) —— **一个文件建全 11 张表**，容器首次启动自动执行。

## 一、总体设计

### 1.1 存储选型

| 存储 | 承担什么 | 为什么用它 |
|---|---|---|
| **MySQL** | 全部**权威数据**：账号、帖子、评论、互动、通知、邮件记录、AI 额度 | 强一致、支持事务、关系清晰 |
| **Redis** | 令牌黑名单、限流计数、邮箱验证码、热帖预览缓存 | 高频读写、天然过期语义 |
| **Elasticsearch** | 帖子**全文检索 + 语义向量检索**（RAG） | MySQL 的 LIKE 无法分词，也不支持 kNN |
| **RustFS**（S3 兼容） | 图片二进制（头像、帖子配图） | 数据库不适合存大对象 |

**核心原则：MySQL 是唯一权威（single source of truth）。** 其他三个都是**派生数据**，随时可以从 MySQL 重建：

- ES 索引：应用启动时 `TopicSearchServiceImpl` 全量重建
- Redis：全部带 TTL，丢了最坏是"用户重新登录一次"
- RustFS：图片有 URL 存在 MySQL 里（`db_account.avatar`、`db_topic.content`），文件本身不可重建 —— 这是唯一的例外

## 二、命名规范

| 项 | 规则 | 示例 |
|---|---|---|
| 表名 | `db_` + 业务名（下划线分隔） | `db_account`、`db_topic_comment` |
| 列名 | 全小写下划线 | `register_time`、`used_tokens` |
| 主键 | 一律 `id` | 关联表也用 `id` 指代用户 |
| 时间列 | `time` 或 `xxx_time` | `time`、`register_time` |
| 布尔列 | `tinyint`，0/1 | `mute`、`banned`、`invisible` |
| 索引 | `idx_` + 列组合 | `idx_type_time` |
| 唯一索引 | `uk_` 或语义名 | `uk_email`、`tid_uid_like` |

**Java 侧映射**：MyBatis-Plus 默认开启**驼峰转下划线**，实体类字段 `registerTime` 自动对应列 `register_time`，不需要写 XML。

## 三、表结构详细设计

### 3.1 `db_account` —— 用户账号

```sql
CREATE TABLE `db_account` (
  `id`            int          NOT NULL AUTO_INCREMENT COMMENT '用户 id，自增',
  `username`      varchar(255) DEFAULT NULL                COMMENT '用户名',
  `password`      varchar(255) DEFAULT NULL                COMMENT 'BCrypt 加密后的密码，不存明文',
  `email`         varchar(255) DEFAULT NULL                COMMENT '邮箱，用于登录和找回密码',
  `role`          varchar(255) DEFAULT NULL                COMMENT '角色：user / admin',
  `avatar`        varchar(255) DEFAULT NULL                COMMENT '头像 URL（对象存储里的文件地址）',
  `register_time` datetime     DEFAULT NULL                COMMENT '注册时间',
  `mute`          tinyint      DEFAULT 0                   COMMENT '禁言：1=禁止发帖/评论',
  `banned`        tinyint      DEFAULT 0                   COMMENT '封禁：1=禁止登录',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`),
  UNIQUE KEY `uk_email` (`email`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户账号';
```

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | int | **PK, AUTO_INCREMENT** | 用户唯一标识，其他表所有"用户"列都指向它 |
| `username` | varchar(255) | **UNIQUE** | 用户名，登录用 |
| `password` | varchar(255) | | **BCrypt 密文**，永不存明文；长度给 255 是因为 BCrypt 输出 60 字符，留足余量 |
| `email` | varchar(255) | **UNIQUE** | 邮箱，也可用于登录（`findAccountByNameOrEmail`） |
| `role` | varchar(255) | | `user` / `admin`，Spring Security 权限来源 |
| `avatar` | varchar(255) | | 头像的**完整 URL**（指向 RustFS），不是文件路径 |
| `register_time` | datetime | | 注册时间 |
| `mute` | tinyint | DEFAULT 0 | **禁言**：还能登录、浏览、点赞，但发帖/评论被业务层拒绝 |
| `banned` | tinyint | DEFAULT 0 | **封禁**：登录直接被拒；**已签发的令牌也会被拉黑** |

**`banned` 为什么要拉黑已有令牌？**

封禁发生在用户已登录之后。如果只在登录时检查，那个用户手上的**旧令牌还能继续用**，封禁形同虚设。所以 `JwtAuthorizeFilter` 每次请求都会查一次 `db_account.banned`，为 1 就把令牌写进 Redis 黑名单。

### 3.2 `db_account_details` —— 用户详细资料

```sql
CREATE TABLE `db_account_details` (
  `id`     int          NOT NULL                COMMENT '用户 id，与 db_account.id 一致',
  `gender` int          DEFAULT 0               COMMENT '性别：0=保密 1=男 2=女',
  `phone`  varchar(255) DEFAULT NULL            COMMENT '手机号',
  `qq`     varchar(255) DEFAULT NULL            COMMENT 'QQ 号',
  `wx`     varchar(255) DEFAULT NULL            COMMENT '微信号',
  `desc`   varchar(255) DEFAULT NULL            COMMENT '个人简介',
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户详细资料';
```

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | int **PK（非自增）** | 与 `db_account.id` **一一对应**，一个用户一行 |
| `gender` | int | 0=保密 / 1=男 / 2=女 |
| `phone` / `qq` / `wx` | varchar(255) | 联系方式 |
| `desc` | varchar(255) | 个人简介。**`desc` 是 MySQL 保留字**，必须加反引号 |

**为什么拆成两张表？**

资料字段**不是所有用户都有**，而且**访问频率差别大**：登录、发帖、显示用户名时只需查 `db_account`；只有打开个人主页才需要资料。拆开后主表更小、更热，缓存命中率更高。

**`desc` 保留字的处理** —— 实体类里显式声明：

```java
@TableField("`desc`")
String desc;
```

### 3.3 `db_account_privacy` —— 隐私开关

```sql
CREATE TABLE `db_account_privacy` (
  `id`     int        NOT NULL                COMMENT '用户 id，与 db_account.id 一致',
  `phone`  tinyint(1) NOT NULL DEFAULT 1      COMMENT '手机号是否公开',
  `email`  tinyint(1) NOT NULL DEFAULT 1      COMMENT '邮箱是否公开',
  `wx`     tinyint(1) NOT NULL DEFAULT 1      COMMENT '微信是否公开',
  `qq`     tinyint(1) NOT NULL DEFAULT 1      COMMENT 'QQ 是否公开',
  `gender` tinyint(1) NOT NULL DEFAULT 1      COMMENT '性别是否公开',
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户隐私开关';
```

- **1 = 公开，0 = 仅自己可见**（默认全公开）
- **不给历史用户预填数据**：Service 层用 `orElse` 兜底，查不到就按"全部公开"处理，老用户不需要补数据行
- 默认值给 1 是**有意的选择**：宁可让用户发现"资料默认公开"后去关闭，也不要默认全隐藏导致个人主页一片空白

### 3.4 `db_account_ai_usage` —— AI 用量与周额度

```sql
CREATE TABLE `db_account_ai_usage` (
  `uid`          int      NOT NULL COMMENT '用户 id',
  `used_tokens`  bigint   NOT NULL DEFAULT 0 COMMENT '本周已用 token 数（参与额度判断）',
  `total_tokens` bigint   NOT NULL DEFAULT 0 COMMENT '累计已用 token 数（只做统计，不参与限制）',
  `week_start`   date     NOT NULL COMMENT '本条统计所属周的周一，用于跨周重置',
  `update_time`  datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`uid`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='AI 用量与周额度';
```

**这是全库最巧的一张表 —— 用 `week_start` 代替定时任务。**

常规做法是写定时任务每周一 0 点清零，但那样有两个问题：服务周一没开机 → 重置丢失；多实例部署 → 定时任务重复执行。

这里改成**读时判断**：

```java
if (!record.getWeekStart().equals(本周周一)) {
    重置 usedTokens = 0，weekStart = 本周周一
}
```

- **不需要定时任务**，也就不怕服务停机
- **天然幂等**，多实例同时判断也不会算错
- 额度和统计**分两列**：`used_tokens` 跨周清零，`total_tokens` 永远累加

### 3.5 `db_topic` —— 帖子

```sql
CREATE TABLE `db_topic` (
  `id`        int NOT NULL AUTO_INCREMENT,
  `title`     varchar(255) DEFAULT NULL,
  `intro`     text,
  `content`   text COMMENT 'Quill Delta JSON',
  `uid`       int DEFAULT NULL,
  `type`      int DEFAULT NULL,
  `time`      datetime DEFAULT NULL,
  `top`       tinyint DEFAULT 0,
  `locked`    tinyint DEFAULT 0,
  `invisible` tinyint DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_type_time` (`type`, `time`),
  KEY `idx_time` (`time`),
  KEY `idx_uid` (`uid`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

| 列 | 说明 |
|---|---|
| `title` | 标题，**不加索引**（不需要按标题精确查，全文搜索交给 ES） |
| `intro` | **纯文本摘要**，由 Service 从正文提取，用于列表页和 ES 索引 |
| `content` | **Quill Delta JSON**（富文本）。存 JSON 而不存 HTML：结构可逆、能重新渲染，也没有 XSS 注入面 |
| `uid` | 作者 id → `db_account.id` |
| `type` | 分类 id → `db_topic_type.id` |
| `time` | 发布时间（同时用于排序） |
| `top` / `locked` / `invisible` | 置顶 / 锁定评论 / 隐藏 |

**三个索引各自支撑什么查询**：

| 索引 | 支撑的查询 |
|---|---|
| `idx_type_time (type, time)` | **按分类查列表 + 按时间倒序** —— 最常用的页面 |
| `idx_time (time)` | **全站最新帖子**（不带分类过滤） |
| `idx_uid (uid)` | **查看某人发的帖子** |

**为什么 `top` / `locked` / `invisible` 不进索引？** 它们的**区分度极低**（绝大多数是 0），建了 MySQL 也不会走。正常做法是"先用 time 索引拿到候选，再过滤"，这个数据量下完全够用。

### 3.7 `db_topic_comment` —— 评论

```sql
CREATE TABLE `db_topic_comment` (
  `id`      int NOT NULL AUTO_INCREMENT,
  `uid`     int DEFAULT NULL,
  `tid`     int DEFAULT NULL,
  `content` text,
  `time`    datetime DEFAULT NULL,
  `quote`   int DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_tid_time` (`tid`, `time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**`quote` 列的设计**：

| 值 | 含义 |
|---|---|
| `-1` | **直接回复帖子**（一级评论） |
| 正整数 | 被回复的**评论 id**（二级回复） |

**为什么不用 `parent_id` + `root_id` 那套？** 这个项目只做**两级**评论（回复楼中楼的某一条），一个 `quote` 足够表达。层级再深才需要闭包表或路径枚举，那是过度设计。

**索引 `(tid, time)`**：页面永远是"查某个帖子下的评论，按时间排"，联合索引直接覆盖。

### 3.8 / 3.9 点赞与收藏

```sql
CREATE TABLE `db_topic_interact_like` (
  `tid`  int DEFAULT NULL,
  `uid`  int DEFAULT NULL,
  `time` datetime DEFAULT NULL,
  UNIQUE KEY `tid_uid_like` (`tid`, `uid`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

（`db_topic_interact_collect` 结构完全相同，唯一索引名为 `tid_uid_collect`）

**核心是那个联合唯一索引** —— 它让"同一用户对同一帖子点两次赞"在**数据库层面**就不可能发生：

```sql
INSERT IGNORE INTO db_topic_interact_like (tid, uid, time) VALUES (?, ?, NOW());
```

**为什么不做计数器列？** 点赞数用 `COUNT(*)` 实时算。有 `(tid, uid)` 索引后 `WHERE tid = ?` 能走索引，一页 10 条的统计完全够快。加计数器列要处理"取消点赞"的原子性，反而更复杂。

### 3.10 `db_notification` —— 站内通知

```sql
CREATE TABLE `db_notification` (
  `id`      int NOT NULL AUTO_INCREMENT,
  `uid`     int DEFAULT NULL COMMENT '接收者用户 id',
  `title`   varchar(255) DEFAULT NULL,
  `content` varchar(255) DEFAULT NULL,
  `type`    varchar(255) DEFAULT NULL,
  `url`     varchar(255) DEFAULT NULL COMMENT '点开后跳转的前端路由',
  `time`    datetime DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_uid_time` (`uid`, `time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- `uid` 是**接收者**（不是触发者）。触发者信息写在 `content` 文本里 —— 这个项目不需要"查看谁赞了我"的关系链
- `url` 存**前端路由**（如 `/index/forum/topic/12`），点通知直接跳转
- `idx_uid_time (uid, time)` 支撑唯一的查询模式：**查我的通知，按时间倒序**

### 3.11 `db_email_record` —— 邮件发送记录

```sql
CREATE TABLE `db_email_record` (
  `id`      int NOT NULL AUTO_INCREMENT,
  `email`   varchar(255) DEFAULT NULL,
  `title`   varchar(255) DEFAULT NULL,
  `content` varchar(255) DEFAULT NULL,
  `time`    datetime DEFAULT NULL,
  `status`  tinyint DEFAULT NULL COMMENT '0=发送中 1=成功 2=失败',
  PRIMARY KEY (`id`),
  KEY `idx_time` (`time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**它是 RabbitMQ 死信队列的"状态载体"**：

```
用户注册 → 投递 MQ 消息（存 email/title/content，status=0）
              ↓
         邮件发送成功 → status=1
              ↓ 失败且重试耗尽
         进入死信队列 → status=2
```

- 邮件发送**异步化**：注册接口不等 SMTP，直接返回
- 发送失败**不丢消息**：进死信队列后可人工重投
- **不与 `db_account` 关联**：注册**之前**就要发验证码，那时候用户还不存在

## 四、索引设计汇总

| 表 | 索引名 | 列 | 类型 | 支撑的查询 |
|---|---|---|---|---|
| `db_account` | PRIMARY | `id` | 主键 | 按 id 查用户 |
| `db_account` | `uk_username` | `username` | 唯一 | 登录查重、按用户名登录 |
| `db_account` | `uk_email` | `email` | 唯一 | 邮箱查重、按邮箱登录/找回密码 |
| `db_topic` | PRIMARY | `id` | 主键 | 帖子详情 |
| `db_topic` | `idx_type_time` | `type, time` | 普通 | **分类列表（过滤+排序）** |
| `db_topic` | `idx_time` | `time` | 普通 | 全站最新 |
| `db_topic` | `idx_uid` | `uid` | 普通 | 某人的帖子 |
| `db_topic_comment` | `idx_tid_time` | `tid, time` | 普通 | 帖子的评论列表 |
| `db_topic_interact_like` | `tid_uid_like` | `tid, uid` | **唯一** | 防重复点赞 + 统计点赞数 |
| `db_topic_interact_collect` | `tid_uid_collect` | `tid, uid` | **唯一** | 防重复收藏 + 统计收藏数 |
| `db_notification` | `idx_uid_time` | `uid, time` | 普通 | 我的通知列表 |
| `db_email_record` | `idx_time` | `time` | 普通 | 按时间查发送记录 |

**联合索引的列顺序原则：等值条件在前，范围/排序列在后。**

以 `idx_type_time (type, time)` 为例：

```sql
SELECT * FROM db_topic WHERE type = 2 ORDER BY time DESC LIMIT 10;
--                            ↑ 等值        ↑ 排序（范围）
```

`type` 在前可以直接定位，`time` 在后天然有序，**不需要额外排序**。反过来建 `(time, type)` 就只能用 `time` 做范围扫描，`type` 过滤退化成回表逐行判断。

## 五、其他存储的键设计

### 5.1 Redis 键

全部定义在 [`Const.java`](Jwt-backend/src/main/java/com/example/utils/Const.java)，统一用 `业务:用途:标识` 的冒号分层。

| 键模式 | 值 | TTL | 用途 |
|---|---|---|---|
| `jwt:blacklist:{jwtId}` | `"1"` | 令牌剩余有效期 | **退出登录 / 封禁**后让令牌立即失效 |
| `jwt:frequency:{username}` | 计数 | 冷却窗口 | 防刷令牌（同一用户频繁申请） |
| `banned:block:{username}` | `"1"` | 封禁时长 | 恶意刷令牌的临时封禁 |
| `verify:email:limit:{email}` | 计数 | 短窗口 | 验证码**发送频率限制**（防轰炸） |
| `verify:email:data:{email}` | 6 位数字 | **3 分钟** | 邮箱验证码本体 |
| `flow:counter:{ip}:{path}` | 计数 | 统计窗口 | 接口限流计数 |
| `flow:block:{ip}:{path}` | `"1"` | 封禁时长 | 限流超限后的封禁 |
| `topic:preview:{id}` | JSON | 短 TTL | **热帖预览缓存** |
| `forum:topic:create:{uid}` | 计数 | 滑动窗口 | 发帖频率限制 |
| `forum:topic:comment:{uid}` | 计数 | 滑动窗口 | 评论频率限制 |
| `ai:chat:counter:{uid}` | 计数 | 滑动窗口 | AI 调用频率限制 |

**为什么全部带 TTL？** Redis 在这套设计里**不存任何权威数据** —— 丢了最坏的情况是"用户重新登录一次"、"验证码重发一次"。这让 Redis 不需要持久化保证，也就没有数据一致性负担。

### 5.2 Elasticsearch 索引

索引名 **`topic`**，对应 [`TopicIndex.java`](Jwt-backend/src/main/java/com/example/entity/dto/TopicIndex.java)。

| 字段 | ES 类型 | 用途 |
|---|---|---|
| `id` | keyword（主键） | 帖子 id，搜到后**回 MySQL 查详情** |
| `title` | text | 标题，查询时 `title^2` **权重加倍** |
| `text` | text | 摘要（来自 `db_topic.intro`） |
| `invisible` | integer | 隐藏帖过滤（`term invisible = 0`） |
| `denseVector` | **dense_vector (1024)** | **语义向量**，RAG 检索用 |

**要点一：ES 不存帖子完整内容。**

ES 只负责"按关键词/语义找出相关帖子的 **id**"，拿到 id 后仍回 MySQL 查详情。这样索引小、重建快，也不会出现"ES 里的统计数和 MySQL 不一致"这类同步问题。代价是多一次数据库查询 —— 对一页 10 条完全值得。

**要点二：1024 维来自 embedding 模型的硬约束。**

```java
@Field(type = FieldType.Dense_Vector, dims = 1024)
List<Float> denseVector;
```

维度必须与 embedding 模型输出一致（阿里百炼 `text-embedding-v3` 输出 1024 维）。

> ⚠️ **换 embedding 模型时必须改这个数字，并且索引要重建** —— ES 不允许直接修改已有字段的维度。

**RAG 检索流程**：

```
用户提问
   ↓ EmbeddingModel 把问题向量化（1024 维）
   ↓ ES kNN 检索：num_candidates=50 粗筛 → 取 topK=3
   ↓ 拿到帖子 id，回 MySQL 查标题和摘要
   ↓ 组装进 prompt（最多 3 篇、每篇摘要截断 400 字、总上限 1500 字）
   ↓ 交给大模型生成回答，同时把引用来源返回给前端
```

### 5.3 RustFS 对象存储

| 项 | 值 |
|---|---|
| Bucket | `forum` |
| 端口 | 9000（S3 API）/ 9001（控制台） |
| 桶策略 | **公开读**（图片要能被 `<img>` 直接引用） |
| 数据库里的引用 | `db_account.avatar` 存**完整 URL**；帖子配图 URL 在 `db_topic.content` 的 Delta JSON 里 |

**自动建桶**：应用启动时 `S3StorageUtils` 检查桶是否存在，不存在就创建并设为公开读，**不需要手工去控制台操作**。

## 六、设计决策记录

### 1. Quill 富文本存 Delta JSON，不存 HTML

| | 存 HTML | **存 Delta JSON（本项目）** |
|---|---|---|
| XSS 风险 | 高（要严格过滤） | **低**（JSON 结构，前端渲染时再转换） |
| 可逆性 | 有损 | **可完全还原** |
| 体积 | 大 | 小 |
| 服务端处理 | 要解析 HTML | **当作不透明字符串，不解析** |

后端**完全不需要理解正文结构** —— 它只负责存和取。

### 2. 周额度用 `week_start` 而不是定时任务

见 3.4 节。核心是：**用数据表达状态，而不是用调度器**。带来的是"服务停机不影响正确性"和"多实例天然幂等"。

### 3. 点赞用唯一索引 + INSERT IGNORE，不做"先查后插"

```sql
-- ❌ 有并发竞态：两个请求同时查到"没点过"，然后都插入
SELECT COUNT(*) FROM db_topic_interact_like WHERE tid=? AND uid=?;
IF 0 THEN INSERT ...;

-- ✅ 数据库保证唯一，一条 SQL 搞定
INSERT IGNORE INTO db_topic_interact_like (tid, uid, time) VALUES (?, ?, NOW());
```

**把并发正确性交给数据库**，而不是应用层的逻辑判断。

### 4. 不建外键约束

表之间的关联（`db_topic.uid` → `db_account.id`）**只用普通列表达，不建 FOREIGN KEY**：

| 理由 | 说明 |
|---|---|
| **性能** | 外键在每次写入时都要检查父表，高并发下是额外开销 |
| **运维** | 加外键后删除/重建表的顺序被锁死，数据迁移很麻烦 |
| **应用层已有约束** | 业务逻辑保证只写入合法 uid；删除用户用逻辑删除而非物理删除 |
| **为分库分表留余地** | 一旦分库，跨库外键根本无法实现 |

**代价**：可能出现"孤儿数据"（比如手工删了用户，帖子还在）。这个项目里可以接受 —— 展示时 `LEFT JOIN` 查不到用户就显示"已注销"。

### 5. 主键用自增 int，不用 UUID

| | 自增 int | UUID |
|---|---|---|
| 索引大小 | 4 字节 | 16 字节 |
| 插入性能 | **顺序写入，页分裂少** | 随机写入，B+ 树频繁分裂 |
| 可读性 | 好（`/topic/12`） | 差 |
| 分布式唯一性 | 单库够用 | 强 |

**不选 UUID 的原因**：这个项目是**单库**，没有分布式 ID 需求。而自增主键的**顺序写入**对 InnoDB 聚簇索引非常友好 —— 数据按主键物理排序，插入永远在末尾，不产生页分裂。

> 唯一例外是 `db_account_details.id` —— 它**不是自增**，因为它的值**就是** `db_account.id`。

### 6. 表名统一 `db_` 前缀

避免和 MySQL 保留字冲突（`order`、`group`、`user` 都是保留字），也方便一眼区分业务表和系统表。

## 七、初始化与维护

### 7.1 一键初始化

```powershell
# Docker：容器首次启动自动执行 schema.sql
docker compose up -d mysql

# 手工执行
docker exec -i forum-mysql mysql -uroot -p123456 < Jwt-backend/sql/schema.sql
```

[`Jwt-backend/sql/schema.sql`](Jwt-backend/sql/schema.sql) 是**唯一的建表入口**，包含全部 11 张表。

**执行机制**：`docker-compose.yml` 把 `sql/` 挂载到容器的 `/docker-entrypoint-initdb.d`，MySQL 官方镜像在**数据目录为空时**会执行该目录下**所有 `.sql` 文件**。

**子目录 `legacy/` 里的文件为什么不会被执行**：entrypoint 脚本**不递归**子目录，日志里会明确显示 `ignoring /docker-entrypoint-initdb.d/legacy`。

### 7.2 历史脚本的处理

早期把建表拆成 4 个文件（`forum_schema` / `phase3` / `phase4` / `phase5`），有两个问题：

1. **顺序靠文件名巧合** —— `forum_schema` 恰好排在 `phase3` 前面
2. **`phase3` 要给 `db_account` 加列，但那张表没有任何脚本** → 全新环境初始化时 phase3 报错中断，**导致 phase4、phase5 全都没执行**

合并成 `schema.sql` 后两个问题都消失：顺序写死在文件里，`db_account` 建表时直接包含那 3 列（于是连 `DELIMITER` 存储过程都不需要了）。

原文件移到 `sql/legacy/` 留档。

### 7.3 备份与恢复

```powershell
# 备份
docker exec forum-mysql mysqldump -uroot -p123456 template > D:\backup\forum.sql

# 恢复
Get-Content D:\backup\forum.sql | docker exec -i forum-mysql mysql -uroot -p123456 template
```

**数据物理位置**：Docker 命名卷 `jwt_mysql-data`，实际在 WSL2 虚拟磁盘里：

```
C:\Users\<用户>\AppData\Local\Docker\wsl\disk\docker_data.vhdx
```

Windows 资源管理器里**看不到里面的文件**，必须通过 `docker exec` 或客户端连接访问。

### 7.4 重建数据库

```powershell
docker compose stop mysql
docker rm forum-mysql
docker volume rm jwt_mysql-data     # ⚠️ 数据全丢
docker compose up -d mysql          # 自动重新执行 schema.sql
```

## 八、规模评估

当前数据量（开发环境）：`db_topic_type` 4 行（初始分类），其余全为 0 行。

**设计能支撑的规模**（单机 MySQL 8）：

| 表 | 预估瓶颈 | 应对 |
|---|---|---|
| `db_topic` | 百万级时 `COUNT(*)` 变慢 | 加计数器列或缓存 |
| `db_topic_interact_like` | 千万级（每人每次点赞一行） | 按 `tid` 分片，或按月分表 |
| `db_notification` | 千万级且持续增长 | **定时归档**（只留 3 个月） |
| `db_email_record` | 同上 | 定期清理 |

**当前判断**：这个项目是**校园论坛**量级（万级用户、十万级帖子），现有设计和索引**完全够用**，不需要分库分表。
