## 二、整体架构

### 2.1 分层结构

```
┌──────────────────────────────────────────────────────────┐
│  浏览器（Vue 3 + Element Plus + Quill）                    │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTP / SSE
                        │（dev: vite 代理 / prod: Nginx 反代）
┌───────────────────────▼──────────────────────────────────┐
│  过滤器链（顺序很重要）                                     │
│  CorsFilter → FlowLimitFilter → TraceIdFilter             │
│    → JwtAuthorizeFilter → Spring Security FilterChain     │
└───────────────────────┬──────────────────────────────────┘
┌───────────────────────▼──────────────────────────────────┐
│  Controller（8 个，含 admin 子包）                         │
└───────────────────────┬──────────────────────────────────┘
┌───────────────────────▼──────────────────────────────────┐
│  Service（12 个接口 + 实现）                               │
│    · 业务逻辑  · 事务  · 缓存失效  · 索引同步               │
└───────────────────────┬──────────────────────────────────┘
┌───────────────────────▼──────────────────────────────────┐
│  Mapper（MyBatis-Plus 9 个）│ Repository（ES 1 个）        │
└───────────────────────┬──────────────────────────────────┘
                        │
     ┌──────────────────┼──────────────────┬──────────────┐
     ▼                  ▼                  ▼              ▼
┌─────────┐       ┌─────────┐       ┌──────────┐   ┌──────────┐
│  MySQL  │       │  Redis  │       │    ES    │   │  RustFS  │
│ (权威)   │       │ (TTL)   │       │ (可重建)  │   │ (URL引用) │
└─────────┘       └─────────┘       └──────────┘   └──────────┘
                                                    ┌──────────┐
                                                    │ RabbitMQ │
                                                    │ (异步)   │
                                                    └──────────┘
```

### 2.2 核心原则：MySQL 是唯一权威

| 存储 | 存什么 | 能否重建 | 挂了怎么办 |
|---|---|---|---|
| **MySQL** | 全部业务数据 | ❌ **不能** | 业务直接失败 |
| **Redis** | 令牌黑名单 / 限流计数 / 验证码 / 列表缓存 | ✅ 全部带 TTL | 用户重新登录 / 缓存穿透一次 |
| **Elasticsearch** | 帖子 id + 标题 + 摘要 + 向量 | ✅ **启动时全量重建** | 搜索不可用，其他正常 |
| **RustFS** | 图片二进制 | ⚠️ **不能**（但 URL 在 MySQL 里） | 图片显示不出来 |

**这个边界非常重要** —— 只有 MySQL 需要强一致，其他都可以"坏了就重建"，系统整体不会因为某个中间件挂掉而全盘崩溃。

### 2.3 请求的生命周期（以"发帖"为例）

```
① 前端 POST /api/forum/create-topic
        │
② CorsFilter          预检 + 白名单
        │
③ FlowLimitFilter     全局限流（3 秒 10 次）+ 业务级频率限制
        │
④ TraceIdFilter       生成 traceId，注入 MDC，响应头返回
        │
⑤ JwtAuthorizeFilter  验签 → 查封禁标记 → 把 userId 挂到 request
        │
⑥ Spring Security     鉴权（/api/forum/** 需登录）
        │
⑦ ForumController     参数校验（@Valid）
        │
⑧ TopicServiceImpl
     ├─ 违禁词检查
     ├─ 存 MySQL（db_topic）
     ├─ 删列表缓存（topic:preview:*）
     └─ 同步 ES 索引（含向量化，失败不阻塞）
        │
⑨ 返回 RestBean<null>
```

**注意 ⑤ 和 ⑧ 之间的分工**：过滤器只负责"你是谁"，业务层负责"能不能做"。

## 三、认证与安全

### 3.1 JWT 无状态认证

**令牌里装什么**：

```java
// JwtUtils.createJwt
{
  "id": 1,                          // 用户 id
  "name": "tomocat",                // 用户名
  "authorities": ["ROLE_user"],     // 权限
  "exp": <7 天后>,                  // 过期时间
  "jti": "<uuid>"                   // 令牌唯一 id（黑名单用这个做 key）
}
```

**签名算法**：HMAC256，密钥在 `application-local.yml`（不进版本库）。

### 3.2 核心设计：JWT 的「无状态」与「能踢人」如何兼得

**这是整个认证模块最值得讲的地方。**

**问题**：JWT 是无状态的 —— 令牌签发后，服务端没有任何办法单方面宣布它失效。但业务需要：

- 用户点"退出登录" → 令牌应立刻失效
- 管理员封禁用户 → 该用户手上的令牌应立刻失效

**两种解法**：

| 方案 | 做法 | 代价 |
|---|---|---|
| ❌ 每请求查库 | 每次请求 `SELECT * FROM db_account WHERE id = ?` | 把 JWT 的优势全抵消（每请求一次 DB） |
| ✅ **Redis 黑名单** | 只在"需要失效"时把 `jti` 写进 Redis（TTL = 令牌剩余有效期），过滤器查一次 Redis | 每请求一次 Redis（内存级，可忽略） |

**实现**：

```java
// 退出登录 / 封禁时
utils.invalidateJwt(authorization);   // 写 jwt:blacklist:<jti>，TTL 到令牌过期

// 过滤器里
if (utils.isInvalid(jwt)) { /* 视为未登录 */ }
```

**为什么 TTL 到令牌过期就够**：令牌过期后本来就无效了，黑名单再留着是浪费内存。

### 3.3 过滤器链的顺序

```
CorsFilter              ← 第一：预检请求要能被处理，否则前端全挂
  ↓
FlowLimitFilter         ← 第二：限流要在最前面，挡掉刷接口的
  ↓
TraceIdFilter           ← 第三：生成 traceId，后面所有日志都带它
  ↓
JwtAuthorizeFilter      ← 第四：解析令牌、查封禁、挂 userId
  ↓
Spring Security Chain   ← 第五：鉴权（哪些路径要登录 / 哪些要 admin）
```

**几个容易搞错的点**：

| 点 | 说明 |
|---|---|
| **CORS 必须最先** | 预检 OPTIONS 请求不带令牌，如果被后面的过滤器拦了，前端会看到 CORS 错误 |
| **限流在鉴权前** | 未登录的机器人也要限流，不能等鉴权 |
| **traceId 在鉴权前** | 后面所有日志（包括鉴权失败的）都要有 traceId |
| **JwtAuthorizeFilter 不是 SecurityFilter** | 它是自己写的 `OncePerRequestFilter`，注册在 Security 链之前，只负责"解析 + 挂属性"，不做拒绝 |

### 3.4 三层限流

| 层 | 粒度 | 配置 | 作用 |
|---|---|---|---|
| **全局** | IP + 路径 | `3 秒 10 次`，超了封禁 30 秒 | 挡脚本刷接口 |
| **业务级** | 用户 | `forum:topic:create:{uid}` 等 | 防单个用户高频发帖 |
| **登录熔断** | 用户名 | `jwt:frequency:{username}` + `banned:block:{username}` | 防暴力申请令牌（阶梯式延长封禁） |

**为什么分三层**：全局挡"机器"，业务级挡"人"，登录熔断挡"专门攻击令牌签发"。三者时间窗口和惩罚策略不同，混在一起会误伤。

### 3.5 封禁 vs 禁言

| | `banned`（封禁） | `mute`（禁言） |
|---|---|---|
| 能登录吗 | ❌ 不能（登录接口直接拒） | ✅ 能 |
| 能浏览吗 | ❌（登不进来） | ✅ 能 |
| 能发帖/评论吗 | —（进不来） | ❌ 被业务层拒 |
| 已签发令牌 | **立刻拉黑** | 不处理（权限还在，只是写操作被拒） |

**封禁为什么要拉黑已签发令牌**：封禁发生在用户已登录之后。如果只在登录时检查，旧令牌还能继续用 —— 封禁形同虚设。所以 `JwtAuthorizeFilter` 每次请求都查 `banned:block:{uid}`，命中就拉黑。

**禁言为什么不拉黑令牌**：禁言只限制"写"，用户还能正常浏览、点赞。拉黑会导致他连看都看不了 —— 惩罚过重。

### 3.6 密码与敏感数据

| 项 | 做法 |
|---|---|
| **密码存储** | BCrypt 哈希（自带盐 + 慢哈希），**永不存明文** |
| **改密码** | 必须先校验原密码（否则令牌泄露就能直接改密码占号） |
| **隐私字段** | 五项开关，**服务端过滤**（绕过前端也拿不到） |
| **敏感配置** | `application-local.yml` / `.env` 全部 gitignore |
| **日志** | 不打印密码、令牌、密钥 |

**隐私字段服务端过滤**：

```java
List<String> hidden = self ? List.of() : privacy.hiddenFields();
// hidden 里的字段在 VO 里置 null —— 前端拿不到值，直接调接口也一样
```

## 四、论坛核心

### 4.1 富文本为什么存 Delta JSON 而不是 HTML

| | 存 HTML | ✅ **存 Delta JSON** |
|---|---|---|
| XSS 风险 | 高（要严格过滤标签/属性） | **低**（JSON 结构，前端渲染时再转） |
| 可逆性 | 有损（编辑器回填会失真） | **完整还原** |
| 后端处理 | 要解析 HTML | **当作不透明字符串**，只存不解析 |
| 体积 | 大（带标签） | 小 |

**关键点**：后端完全不需要理解正文结构。它只负责存取，渲染在前端用 Quill 完成。

### 4.2 发帖的完整链路

```java
// TopicServiceImpl.createTopic
1. 检查违禁词（只匹配文字节点）
2. topic.setContent(vo.getContent().toJSONString())   // Delta 序列化
3. topic.createIntro()                                // 生成摘要
4. this.save(topic)                                   // 存 MySQL
5. cacheUtils.deleteCachePattern("topic:preview:*")   // 列表缓存整体失效
6. searchService.saveIndex(topic)                     // 同步 ES（含向量化）
```

**第 5 步为什么"删"而不是"更新"**：列表缓存 key 按分类/页码组合有很多种，逐个更新必然漏。直接按通配符全删，下次读时重建 —— 简单且不会出错。

### 4.3 评论的「楼中楼」设计

只有一个 `quote` 字段：

| 值 | 含义 |
|---|---|
| `-1` | 直接回复帖子（一级评论） |
| 正整数 | 被回复的评论 id（二级回复） |

**为什么不用 `parent_id` + `root_id`**：这个项目只做**两级**评论。层级再深才需要闭包表或路径枚举 —— 那是过度设计。

### 4.4 点赞收藏：把并发正确性交给数据库

**❌ 常见错误写法**：

```java
int count = mapper.selectCount(...eq("tid", tid).eq("uid", uid));
if (count == 0) {
    mapper.insert(like);   // ← 两个并发请求会同时判断"没点过"，然后都插入
}
```

**✅ 本项目写法**：

```sql
UNIQUE KEY `tid_uid_like` (`tid`, `uid`)
```
```java
INSERT IGNORE INTO db_topic_interact_like (tid, uid, time) VALUES (?, ?, NOW());
```

**唯一索引 + `INSERT IGNORE`** —— 重复插入被数据库静默忽略，**不需要任何应用层判断**。

**为什么不用计数器列**：点赞数用 `COUNT(*)` 实时算。有 `(tid, uid)` 索引后 `WHERE tid = ?` 能走索引，一页 10 条够快。加计数器列要处理"取消点赞"的原子性，反而更复杂。

### 4.5 帖子的三个索引

| 索引 | 支撑的查询 |
|---|---|
| `idx_type_time (type, time)` | **分类列表 + 按时间倒序** —— 最常用页面 |
| `idx_time (time)` | 全站最新（不带分类过滤） |
| `idx_uid (uid)` | 某人发的帖子 |

**列顺序原则：等值条件在前，排序列在后**。`type` 在前能直接定位，`time` 在后天然有序，**不需要额外排序**。反过来建就只能用 `time` 做范围扫描。

**为什么 `top`/`locked`/`invisible` 不进索引**：区分度极低（绝大多数是 0），建了也不会用。

## 五、站内通知

### 5.1 表结构

| 列 | 说明 |
|---|---|
| `uid` | **接收者**（不是触发者） |
| `title` / `content` | 通知内容（触发者名字写在 content 里） |
| `type` | 类型（点赞/评论/系统） |
| `url` | **前端路由**（如 `/index/forum/topic/12`），点通知直接跳 |
| `time` | 配合 `idx_uid_time` 支撑"查我的通知按时间倒序" |

**为什么不建"谁赞了我"的关系表**：不需要完整关系链。触发者信息写在 `content` 文本里就够展示。

### 5.2 触发点只有一处

所有通知都在 `TopicServiceImpl.createComment` 里产生 —— **不为每个场景写一遍**。

### 5.3 为什么通知放在 insert 之后，而不是塞进事务

**通知失败不应该回滚评论** —— 评论已经写成功，通知发不出去是次要问题。

如果塞进同一个事务，通知表一锁、或字段超长，整个评论就失败了 —— **用次要功能的失败拖垮核心功能**。

### 5.4 越权防护

删评论、删帖这类操作，**SQL 里必须带 uid 条件**：

```java
baseMapper.delete(Wrappers.<Topic>query().eq("id", tid).eq("uid", uid));
//                                              ↑ 关键：只能删自己的
```

**不是**先查出来判断 `if (topic.getUid() == uid)` 再删 —— 那样有"检查-使用"的时间窗口。**让 SQL 自己保证**，`affected rows == 0` 就说明不是你的。

## 六、管理后台

### 6.1 权限只需要在一处写

```java
// SecurityConfiguration
.requestMatchers("/api/admin/**").hasRole("admin")
```

**`AccountAdminController` 里没有一行权限判断代码** —— 全部收敛到 Security 配置。加新接口时不用记得写 `if (isAdmin)`。

### 6.2 用强类型 VO，不用 JSONObject

| | 参考实现的写法 | ✅ 本项目写法 |
|---|---|---|
| 代码 | `RestBean<List<JSONObject>>` | `PageRestBean<UserAdminVO>` |
| 字段错字 | **运行时才炸** | **编译期就报错** |
| 前端类型提示 | 无 | 有 |

**代价**是每个响应都要写一个 VO 类；**收益**是重构安全。

### 6.3 分页响应单独抽一层

```java
record RestBean<T>(int code, T data, String message)
record PageRestBean<T>(int code, List<T> list, long total, long page, String message)
```

**为什么不塞进 `RestBean` 的 data 里**：`total` 是给分页组件看的，不是业务数据。混在一起前端要写 `res.data.data.list`，很别扭。

### 6.4 两个防呆

| 防呆 | 原因 |
|---|---|
| **不能修改自己的账号信息** | 管理员把自己封了/降级了，就没人能进后台了 |
| **不能自己改密码** | 应去"个人设置"改（那里校验原密码）；后台改密码是给"重置别人密码"用的 |

## 七、违禁词过滤

### 7.1 词表三级查找

| 顺序 | 位置 | 用途 |
|---|---|---|
| 1 | 配置指定路径（`forum.prohibited-file`） | 生产环境外部挂载，改词表不用重新打包 |
| 2 | `Jwt-backend/prohibited.json` | 开发时直接改 |
| 3 | `classpath:prohibited.json` | 打包兜底 |

**读不到会打 WARN，不会静默放行** —— 过滤功能失效必须能被发现。

### 7.2 为什么用 `CopyOnWriteArrayList`

**读多写极少**：每次发帖/评论都要检查一遍词表（读），改词表是低频操作（写）。

`CopyOnWriteArrayList` 写操作复制整个数组（贵），但读操作**完全无锁**（快）。完美匹配。

### 7.3 只匹配「文字节点」

Quill Delta 是 JSON 数组，里面有文字、图片、链接节点。如果直接对整段 JSON 做字符串匹配：

```
❌ 图片 URL 里恰好包含违禁词 → 误判
❌ 链接地址里包含违禁词 → 误判
```

**正确做法**：解析 Delta → 只取 `insert` 是字符串的文字节点 → 拼接 → 匹配。

### 7.4 后台热更新

管理后台改完词表 → 写文件 → 重新加载到内存（整体替换）→ **立刻生效，不用重启**。

## 八、消息队列与邮件

### 8.1 为什么用 MQ 而不是同步发邮件

| | 同步发邮件 | ✅ **MQ 异步** |
|---|---|---|
| 注册接口耗时 | 几百毫秒 ~ 几秒（SMTP 握手） | **几毫秒** |
| SMTP 挂了 | **注册直接失败** | 消息留在队列，恢复后继续发 |
| 失败重试 | 要自己写循环 | **死信队列**自动记录 |

### 8.2 拓扑

```
注册接口
   ↓ 投递
┌──────────────┐
│ mail 队列     │  ← 消费者 MailQueueListener
│ (TTL + 死信)  │
└──────┬───────┘
       │ 发送成功 → db_email_record.status = 1
       │ 失败且重试耗尽
       ↓
┌──────────────┐
│ error 队列    │  ← 死信队列，status = 2，可人工重投
└──────────────┘
```

### 8.3 一张表让 MQ 可观测

`db_email_record` 记录每次发送：`status` 0=发送中 / 1=成功 / 2=失败（进死信）。

**否则**：MQ 出问题你只能看日志翻记录，有了表可以直接在管理后台列表查看 + 重发。

**为什么不和 `db_account` 关联**：注册**之前**就要发验证码，那时候用户还不存在。

### 8.4 Boot 4 适配：必须换转换器

| 版本 | 转换器 |
|---|---|
| Spring Boot 3.x | `Jackson2JsonMessageConverter`（Jackson 2） |
| **Spring Boot 4.x** | **`JacksonJsonMessageConverter`**（Jackson 3） |

**类名只差一个 `2`，底层完全不是一套。** 用错了会在消费端报序列化失败。

### 8.5 为什么必须抛 `AmqpRejectAndDontRequeueException`

消费失败时，如果抛普通异常，RabbitMQ 会**无限重投** → 死循环刷日志。

抛 `AmqpRejectAndDontRequeueException` 告诉它"**别重投了，直接进死信**" —— 这样失败的消息进 `error` 队列，可人工处理。

### 8.6 队列参数不能随意改

RabbitMQ 的**队列参数不可变**。如果之前跑过旧版本（没有死信配置），启动会报：

```
PRECONDITION_FAILED - inequivalent arg x-dead-letter-exchange
```

**解决**：先删队列（`rabbitmqctl delete_queue mail` 或管理页面删），重启后按新参数重建。

## 九、搜索（Elasticsearch）

### 9.1 索引设计：只存「引用」，不存「副本」

| 字段 | 类型 | 用途 |
|---|---|---|
| `id` | keyword（主键） | 帖子 id，搜到后**回 MySQL 查详情** |
| `title` | text | 标题，查询时 `title^2` **权重加倍** |
| `text` | text | 摘要（`db_topic.intro`） |
| `invisible` | integer | 隐藏帖过滤（`term invisible = 0`） |
| `denseVector` | **dense_vector (1024)** | 语义向量，RAG 用 |

**ES 里没有点赞数、没有正文、没有评论。** 这样：

- 索引小、重建快
- **不会出现"ES 里的数据与 MySQL 不一致"这类问题**

### 9.2 同步策略：增量 + 启动全量重建

| 时机 | 动作 |
|---|---|
| **发帖** | `saveIndex(topic)` |
| **编辑** | 重新查库后 `saveIndex(updated)` |
| **删除**（作者/管理员） | `deleteIndex(id)` |
| **隐藏/恢复** | `saveIndex(topic)` |
| **应用启动** | **全量重建**（清空 + 从 MySQL 重新导入） |

**为什么每次都全量重建**：几千条帖子很快（不到 1 秒），而且**永远不会出现"索引和数据库对不上"的疑难杂症**。数据量真大了再改成增量 + 定时补偿。

### 9.3 同步失败不阻塞业务

```java
try {
    repository.save(index);
} catch (Exception e) {
    log.warn("同步搜索索引失败(id={})：{}", topic.getId(), e.getMessage());
}
```

**ES 挂了，发帖照样成功** —— 下次启动全量重建会补上。

**向量化失败同理**：

```java
catch (Exception e) {
    log.warn("生成向量失败(id={})，该帖将只能被关键词搜到：{}", index.getId(), e.getMessage());
    return false;
}
```

**embedding 服务挂了，帖子仍能被关键词搜到** —— 只是 RAG 检索不到它。

### 9.4 为什么不用 Canal

Canal 是阿里开源的 MySQL binlog 订阅工具，能自动把数据变更同步到下游。**本项目没用它**，原因：

| 条件 | 本项目 |
|---|---|
| 数据量 | **几千条**（全量重建 < 1 秒） |
| 下游数量 | **只有 ES 一个** |
| 团队规模 | 1 人 |

**引入 Canal 的代价**：额外部署 `canal-server` + `canal-adapter`、开 binlog ROW 模式、管理位点、处理 DDL 变更。

**Canal 的价值在"大规模 + 多下游 + 解耦"** —— 这个项目一个条件都不满足。

### 9.5 ES 版本必须 9.x

Spring Data ES 6.0.5 带的客户端是 `elasticsearch-java 9.2.8`。连 **8.x 服务端会返回 400**：

```
[es/indices.exists] Expecting a response body, but none was sent
```

**而 Docker Hub 上的 `elasticsearch` 镜像只到 8.x**（9.x 只在 `docker.elastic.co`，国内加速器不管）。本项目用的 9.5.3 是从 Hub 拉到后打标准标签的。

## 十、对象存储（RustFS）

### 10.1 为什么从 MinIO 换成 RustFS

| | MinIO | ✅ **RustFS** |
|---|---|---|
| 社区版 | **官方已停止发布（AGPL）**，`latest` 标签被撤 | 活跃维护 |
| 协议 | S3 兼容 | **S3 兼容** |
| 端口 | 9000 / 9001 | **9000 / 9001**（完全一致） |
| 语言 | Go | Rust |

**关键**：因为**两者都兼容 S3 协议**，后端用的 `io.minio:minio` SDK 本质就是个**通用 S3 客户端** —— 所以换存储只改了配置项名（`minio.*` → `storage.*`），**代码逻辑一行没动**。

> 这也是一个设计好处的证明：**依赖抽象（S3 协议）而不是具体实现（MinIO）**，换实现成本极低。

### 10.2 数据库里只存 URL

```
图片文件  →  RustFS（二进制）
URL 字符串 →  MySQL（db_account.avatar / db_topic.content 里的 Delta JSON）
```

**没有同步需求** —— 文件上传后不可变。

**删帖子不删图片** —— 会留下**孤儿文件**。这是可接受的取舍（清理需要引用计数机制，不值得）。

### 10.3 自动建桶 + 公开读

应用启动时 `S3StorageUtils` 检查桶是否存在，不存在就创建并设置**公开读策略** —— 这样图片能被 `<img>` 直接引用，不需要每次请求都带签名。

**不需要手工去控制台操作。**

### 10.4 一个部署坑：容器用非 root 用户

RustFS 容器以 **ID 10001 的非 root 用户**运行。如果挂宿主机目录，必须先 `chown 10001`，否则权限拒绝。

**所以 compose 里用的是命名卷**（Docker 自动处理权限）。

## 十一、AI 能力

### 11.1 为什么用 SSE 而不是 WebSocket

| | WebSocket | ✅ **SSE** |
|---|---|---|
| 方向 | 双向 | **单向（服务端→客户端）** |
| 协议 | 升级握手 | **普通 HTTP** |
| 断线重连 | 要自己实现 | **浏览器内置** |
| 适用场景 | 聊天室、协同编辑 | **LLM 流式输出**（只要服务端推） |

**AI 对话只需要"服务端逐字推给前端"** —— 单向就够了，SSE 比 WebSocket 简单得多。

### 11.2 一个关键细节：不能用 `EventSource`

`EventSource` 是浏览器原生的 SSE 客户端，但它**只能发 GET 请求**，且**不能自定义请求头**。

而 AI 对话需要：
- **POST**（要传历史消息、问题、RAG 开关）
- **`Authorization` 头**（要带令牌）

**所以前端用 `fetch` + `ReadableStream` 手动解析 SSE 帧**：

```javascript
const reader = response.body.getReader();
// 手动解析 data: / event: 帧，事件类型有 chunk / refs / error / done
```

### 11.3 RAG 检索链路

```
用户提问
   ↓ EmbeddingModel 向量化（1024 维）
   ↓ ES kNN 检索：num_candidates=50 粗筛 → topK=3
   ↓ 拿到帖子 id，回 MySQL 查标题和摘要
   ↓ 组装 prompt（最多 3 篇 / 每篇摘要截断 400 字 / 总上限 1500 字）
   ↓ 大模型生成回答
   ↓ 同时把引用来源（帖子 id + 标题）返回前端
```

**上下文预算**：一次 RAG 问答约 2000 token（3 篇 × 400 字摘要 + prompt）。

### 11.4 检索层抽象成接口

```java
public interface TopicRetriever {
    List<Topic> retrieve(String question, int topK);
}

// 实现：VectorTopicRetriever（ES kNN）
```

**为什么要抽接口**：将来想换 BM25、或做混合检索，**加个实现类就行，`RagService` 一行不动**。

### 11.5 降级设计

| 故障 | 表现 | 降级行为 |
|---|---|---|
| ES 挂了 | 检索抛异常 | 返回空上下文 → **普通问答**（AI 仍可用） |
| embedding 挂了 | 向量化失败 | 同上 |
| 没配 API key | `available()` 返回 false | 提示"AI 尚未配置" |
| 额度用完 | 前置校验失败 | 返回 `event: error` |

**核心原则：AI 的任何一环挂掉，都不能让整个 AI 功能不可用。**

### 11.6 周 token 额度：不用定时任务

**常规做法**：写定时任务，每周一 0 点清零。**问题**：

- 服务周一没开机 → 重置丢失
- 多实例部署 → 定时任务重复执行

**本项目的做法**：`db_account_ai_usage.week_start` 记录统计所属周，**读取时判断**：

```java
if (!record.getWeekStart().equals(本周周一)) {
    重置 usedTokens = 0，weekStart = 本周周一
}
```

| 优点 | 说明 |
|---|---|
| **不需要定时任务** | 服务停机不影响正确性 |
| **天然幂等** | 多实例同时判断也不会算错 |
| **额度和统计分两列** | `used_tokens` 跨周清零，`total_tokens` 永远累加 |

### 11.7 流式下的额度记账

**问题**：流式响应结束时，怎么知道用了多少 token？

| 场景 | 做法 |
|---|---|
| **非流式** | 用响应里的 `usage.total_tokens`（真实值） |
| **流式** | 百炼的 SSE 最后一个 chunk 带 usage；拿不到时用 `字符数 / 2` 估算 |

**只在调用成功后才记账** —— 失败的请求不扣额度。

## 十二、数据库设计

### 12.1 11 张表

| # | 表 | 说明 |
|---|---|---|
| 1 | `db_account` | 用户账号（登录凭据 / 角色 / 封禁禁言 / 头像） |
| 2 | `db_account_details` | 用户资料（性别 / 手机 / QQ / 微信 / 简介） |
| 3 | `db_account_privacy` | 隐私开关（5 个字段是否公开） |
| 4 | `db_account_ai_usage` | AI 周额度 |
| 5 | `db_topic` | 帖子 |
| 6 | `db_topic_type` | 分类（4 条初始数据） |
| 7 | `db_topic_comment` | 评论 |
| 8 | `db_topic_interact_like` | 点赞 |
| 9 | `db_topic_interact_collect` | 收藏 |
| 10 | `db_notification` | 站内通知 |
| 11 | `db_email_record` | 邮件发送记录 |

**详见** [`数据库设计文档.md`](./数据库设计文档.md)（逐表字段 + 索引理由 + 6 条设计决策）。

### 12.2 为什么不建外键

| 理由 | 说明 |
|---|---|
| **性能** | 外键每次写入都要检查父表，高并发下是额外开销 |
| **运维** | 加外键后删除/重建表的顺序被锁死，数据迁移很麻烦 |
| **应用层已有约束** | 业务保证只写合法 uid；删用户用逻辑删除 |
| **为分库分表留余地** | 一旦分库，跨库外键根本无法实现 |

**代价**：可能出现"孤儿数据"。展示时 `LEFT JOIN` 查不到用户就显示"已注销"。

### 12.3 为什么主键用自增 int 不用 UUID

| | 自增 int | UUID |
|---|---|---|
| 索引大小 | 4 字节 | 16 字节 |
| 插入性能 | **顺序写入，页分裂少** | 随机写入，B+ 树频繁分裂 |
| 可读性 | 好（`/topic/12`） | 差 |
| 分布式唯一 | 单库够用 | 强 |

**本项目是单库**，没有分布式 ID 需求。自增主键的**顺序写入**对 InnoDB 聚簇索引非常友好。

### 12.4 建表脚本的演进（一个踩过的坑）

**早期**把建表拆成 4 个文件：

```
sql/
├── forum_schema.sql      ← 5 张表
├── phase3_schema.sql     ← 2 张表 + 给 db_account 加 3 列   ⚠️ 依赖 db_account
├── phase4_privacy.sql    ← 1 张表
└── phase5_ai_quota.sql   ← 1 张表
                          ⚠️ db_account / db_account_details 哪都没有
```

**两个问题**：

1. **顺序靠文件名巧合**（`forum_schema` 恰好排在 `phase3` 前面）
2. **`phase3` 要给 `db_account` 加列，但那张表没有任何脚本** → 全新环境初始化时 `phase3` 报错中断 → **`phase4`、`phase5` 全都没执行**

**现在的做法**：合并成单一 `sql/schema.sql`（11 张表按依赖顺序排列），`db_account` 建表时**直接包含那 3 列**，连 `DELIMITER` 存储过程都不需要了。

### 12.5 一个隐蔽的编码坑

**MySQL 官方镜像的 entrypoint 执行初始化脚本时，连接字符集默认是 `latin1`。**

```
schema.sql 里的 UTF-8 字节  E697A5（"日"）
        ↓ 被 latin1 解释成 3 个字符
     æ — ¥
        ↓ 按 utf8mb4 存进表
   C3A6 E28094 C2A5     ← 查出来就是 æ—¥å¸¸
```

**这叫"双重编码"（mojibake）。** 解决办法：`schema.sql` 开头加一行 `SET NAMES utf8mb4;`。

> **这是"本地看不出、一部署就暴露"的典型问题** —— 用 Navicat 手工执行不会有（它默认 utf8mb4）。

## 十三、前端架构

### 13.1 三栏骨架只维护一份

```
┌────────┬──────────────────────┬──────────┐
│ 左导航  │   中内容（路由出口）    │ 右个人区  │
│        │                      │          │
│ 校园论坛 │   TopicList.vue      │ 发帖入口  │
│  AI 页  │   TopicDetail.vue    │ 我的      │
│  设置   │   AiChat.vue         │          │
└────────┴──────────────────────┴──────────┘
```

**全部写在 `indexView.vue`**，右栏只在路由以 `/index/forum` 开头时显示；窄于 1100px 时用 media query 收起。

**为什么不做成可复用布局组件**：这个项目只有一种布局。抽组件反而要传一堆 props。

### 13.2 组件职责划分

| 层 | 职责 | 举例 |
|---|---|---|
| **`views/*`** | **发请求**、管页面状态 | `TopicList.vue` 拉列表 |
| **`components/*`** | **只吃 props、只 emit 事件**，不发请求 | `TopicCard.vue` 只渲染 |
| **`net/api/*`** | 接口的唯一出口 | `api/forum.js` 16 个函数 |

**好处**：组件能独立预览，接口变更只影响一处。

### 13.3 数据刷新用「信号」，不用缓存

**问题**：发帖成功后，列表页怎么知道要刷新？

**方案对比**：

| 方案 | 问题 |
|---|---|
| 整页刷新 | 体验差 |
| 引入前端缓存库 | 过度设计 |
| ✅ **信号计数器** | `store.forumRefreshTick++`，列表 `watch` 它重新拉数据 |

```javascript
// 发帖成功后
store.forumRefreshTick++;

// 列表页
watch(() => store.forumRefreshTick, () => loadList());
```

**简单、可靠、零依赖。**

### 13.4 命令式组件要手工补样式

**踩过的坑**：`ElMessage` / `ElMessageBox` 是**命令式 API**（`ElMessage.success(...)`），不走模板组件那条自动按需引入的路径。

而代码里又是显式 `import` 的，等于**绕开了 `ElementPlusResolver` 的样式注入** —— 结果组件一点 CSS 都没有：

| 组件 | 缺样式的表现 |
|---|---|
| `ElMessage` | 少了 `position: fixed`，提示条**掉到页面底部** |
| `ElMessageBox` | 弹窗**不居中**、没有遮罩和背景 |

**解决**：`main.js` 里显式引入它们的样式：

```javascript
import 'element-plus/theme-chalk/el-message.css'
import 'element-plus/theme-chalk/el-message-box.css'
```

> 这个 bug 特别隐蔽 —— **功能正常，只是样式没了**，而且只影响命令式组件，模板里用的组件都正常。

## 十四、部署

### 14.1 5 个中间件全部 Docker 化

| 服务 | 镜像 | 端口 |
|---|---|---|
| MySQL | `mysql:8.0` | 3306 |
| Redis | `redis:7-alpine` | 6379 |
| RabbitMQ | `rabbitmq:4-management-alpine` | 5672 / 15672 |
| Elasticsearch | `elasticsearch:9.5.3` | 9200 |
| RustFS | `rustfs/rustfs:latest` | 9000 / 9001 |

**一条命令**：

```powershell
docker compose up -d mysql redis rabbitmq elasticsearch rustfs
```

### 14.2 后端**不用改任何配置**

因为所有容器端口都**映射到了宿主机**：

```
容器 forum-mysql:3306   →  宿主机 127.0.0.1:3306
容器 forum-rustfs:9000  →  宿主机 127.0.0.1:9000
```

而 `application-dev.yml` 里写的本来就是 `127.0.0.1` —— **照样能用**。

> 只有**后端也在容器里**时，才需要把 `127.0.0.1` 换成服务名（`mysql` / `redis` / `rustfs`）。

### 14.3 Nginx 必须关 SSE 缓冲

```nginx
proxy_buffering off;
proxy_cache     off;
proxy_read_timeout 300s;
```

**原因**：AI 用 SSE 流式输出，Nginx 默认会把响应攒进缓冲区再一起发 —— 前端就看不到"逐字出现"的效果。

**开发环境** `vite.config.js` 的代理也做了同样处理（改 `cache-control` 和 `x-accel-buffering` 头）。

### 14.4 后端调试仍在 IDEA

**Docker 跑中间件 + 本机跑后端** —— 兼顾环境和调试便利。

| | 全 Docker | ✅ **混合** |
|---|---|---|
| 环境一致 | ✅ | ✅（中间件） |
| 断点调试 | ❌ | ✅ |
| 改代码生效 | 要重建镜像 | **秒级重启** |

## 十五、技术决策记录

**这一章是面试最有价值的部分** —— 不是"我用了什么"，而是"**我为什么不用另一个**"。

| # | 选了这个 | 没选那个 | 理由 |
|---|---|---|---|
| 1 | **Redis 黑名单** | 每请求查库 | 查库会抵消 JWT 无状态的优势 |
| 2 | **RabbitMQ** | Kafka | 邮件是"低频 + 要可靠重试"，RabbitMQ 更合适；Kafka 的优势在吞吐和重放 |
| 3 | **增量 + 启动全量重建** | Canal（binlog 订阅） | 数据量小（几千条）、下游只有一个，Canal 的复杂度不划算 |
| 4 | **唯一索引 + INSERT IGNORE** | 先 SELECT 再 INSERT | 后者有并发竞态 |
| 5 | **不用定时任务清额度** | 每周一 0 点定时任务 | 服务停机丢重置、多实例重复执行 |
| 6 | **Quill Delta JSON** | HTML | XSS 面小、可逆、后端不用解析 |
| 7 | **两级评论（quote）** | 无限层级（闭包表） | 只做两级，一个字段够表达 |
| 8 | **自增 int 主键** | UUID | 单库无分布式需求，顺序写入对 InnoDB 更友好 |
| 9 | **不建外键** | 建外键 | 性能、运维、分库分表 —— 代价是可能出现孤儿数据 |
| 10 | **SSE** | WebSocket | AI 只需要单向推送，SSE 更简单 |
| 11 | **RustFS** | MinIO | MinIO 官方停止发布社区版 |
| 12 | **单体应用** | Spring Cloud | 规模小，微服务的复杂度 > 收益 |

### 补充：为什么不用 Spring Cloud

| 场景 | 本项目 |
|---|---|
| 部署形态 | **单体**，一个 jar |
| 团队 | 1 人 |
| 用户量 | 校园论坛量级 |

**引入微服务的代价**：服务拆分、注册中心、网关、链路追踪、分布式事务。

**但如果规模上来**，演进顺序应该是：

1. 先拆**无状态服务**（AI 服务、搜索服务）—— 最容易独立扩展
2. 数据强相关的（用户、帖子）留在一起，**避免分布式事务**

## 十六、面试高频点

### 16.1 「讲一下你的项目」

> 这是一个校园论坛系统，Spring Boot 4 + Vue 3 前后端分离。
>
> **技术上我想说的是四块**：
>
> **第一，认证设计。** JWT 是无状态的，但业务需要"退出登录立刻失效"和"封禁立刻生效"。我用了 Redis 黑名单 + TTL 的方案 —— 只在需要失效时写一个 `jti`，过滤器里查一次内存级存储，兼顾了性能和可控性。
>
> **第二，数据一致性边界。** MySQL 是唯一权威，ES / Redis / 对象存储都是派生数据。ES 用"增量 + 启动全量重建"双保险，而且同步失败不阻塞业务 —— 下次启动能自愈。这样整个系统只有 MySQL 需要强一致。
>
> **第三，AI 能力。** 做了 SSE 流式对话和向量 RAG：问题向量化 → ES kNN 检索 → 组装 prompt → 回答带引用来源。并且做了完整降级 —— ES 或 embedding 挂了自动退回普通问答。
>
> **第四，工程化。** 三层限流、traceId 全链路追踪、多环境配置、Docker 一键部署。

### 16.2 「JWT 怎么实现退出登录」

> JWT 本身无状态，签发后服务端没法作废。所以我维护了一个 Redis 黑名单：退出时把令牌的 `jti` 写进去，TTL 设成令牌剩余有效期（过期后本来就没用了，不占内存）。
>
> 过滤器每次请求查一次 Redis —— 这是"无状态换来的必然账"，但比每请求查数据库便宜得多。

### 16.3 「点赞怎么防重复」

> 用 `(tid, uid)` 联合唯一索引 + `INSERT IGNORE`。
>
> 常见写法是"先 SELECT 判断再 INSERT"，但那有并发竞态 —— 两个请求同时查到"没点过"，然后都插入。把正确性交给数据库的约束，应用层一行判断都不需要。

### 16.4 「ES 和 MySQL 怎么保证一致」

> 我们不追求强一致，因为 ES 是**派生数据**。策略是"写时增量 + 启动时全量重建"。
>
> 全量重建成效的关键是**数据量小**（几千条，不到 1 秒）。增量同步失败不抛异常，只打 WARN —— ES 挂了不影响发帖，下次启动会补上。
>
> 另外 ES 里**只存 id + 标题 + 摘要 + 向量**，不存完整数据。搜到 id 回 MySQL 查详情 —— 这样索引小、重建快，也不会出现"ES 里的点赞数和 MySQL 不一致"这类问题。

### 16.5 「为什么不用 Canal」

> Canal 的价值在"大规模 + 多下游 + 解耦"。我们数据量几千条、下游只有 ES 一个，引入它要额外部署 server + adapter、开 binlog ROW 模式、管理位点 —— 复杂度成本远大于收益。
>
> 数据量涨到百万级、或要同步多个下游时我会引入，因为它基于 binlog 不丢事件，而且把同步逻辑从业务代码里彻底剥离。

### 16.6 「AI 流式怎么实现的」

> 后端用 `SseEmitter`，前端用 `fetch` + `ReadableStream` 手动解析 SSE 帧。
>
> 一个细节：**不能用浏览器原生的 `EventSource`** —— 它只支持 GET 且不能自定义请求头，而我们需要 POST（传历史消息）和 Authorization（带令牌）。
>
> 另外 Nginx 必须关 `proxy_buffering`，否则响应会被攒起来一起发，看不到逐字效果。

### 16.7 「RAG 是怎么做的」

> 用户提问 → 用百炼 `text-embedding-v3` 转成 1024 维向量 → ES 用 `dense_vector` 做 kNN 检索（`num_candidates=50` 粗筛，取 topK=3）→ 拿到帖子 id 回 MySQL 查标题摘要 → 组装进 prompt（3 篇上限、每篇 400 字、总 1500 字）→ 生成回答并把引用来源返回前端。
>
> 检索层抽成了 `TopicRetriever` 接口，将来想换 BM25 或做混合检索，加个实现类就行。
>
> **降级**：ES 或 embedding 挂了返回空上下文，自动退回普通问答，不影响 AI 整体可用。

### 16.8 「遇到过什么难题」

**推荐讲这三个（都是真实的、有技术含量的）**：

| # | 难题 | 怎么解决的 |
|---|---|---|
| 1 | **ES 客户端版本不兼容** | Spring Data ES 6.0.5 的客户端是 9.2.8，连 8.x 服务端返回 400；而 Docker Hub 只有 8.x 镜像 → 从 Hub 拉 9.5.3 打标准标签 |
| 2 | **数据库初始化中文乱码** | MySQL entrypoint 用 latin1 连接执行 SQL → 双重编码；`SET NAMES utf8mb4` 解决 |
| 3 | **命令式组件没样式** | `ElMessage` 绕开 resolver 的样式注入 → 提示条掉到页面底部；显式 import 其 CSS 解决 |

**共同点**：三个都**不在业务代码里**，都是"框架版本 / 容器环境"带来的差异 —— 也正好说明**工程能力不只是写业务逻辑**。
